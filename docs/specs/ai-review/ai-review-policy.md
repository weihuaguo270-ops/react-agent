# AI 代码审核策略

本文件是 [AI 审核与变更保障 Spec](spec.md) 的执行策略。它定义审核维度和 finding 格式，不重新定义总流程生命周期。

## 1. 定位

AI 审核是提交流程中的风险发现环节，作用是帮助人工审查者定位问题、补充运行证据和判断影响范围。它不是 CI 测试的替代品，也不是人工批准的替代品。

AI 审核只对当前 PR 的 `head_sha` 生效。PR 有新 commit、发生 rebase 或 base 分支变化后，必须重新审核；旧审核结果只能作为历史背景。

## 2. 审核时点

| 时点 | 目的 | 最低要求 |
|---|---|---|
| PR 前（可选） | 提前发现明显逻辑、测试和运行问题 | 当前工作树 diff、相关 Spec、受影响测试 |
| PR 创建或更新后 | 形成可追溯的独立机器审核结论 | 当前 `base_sha`、`head_sha`、完整 diff、相关 CI 结果 |
| 合并前 | 复核修复后的问题和最新主干兼容性 | 最新 `head_sha`、最新 CI、未关闭 findings |
| 合并后 | 只做发布/运行观察 | 不改变已合并 PR 的审核结论 |

PR 前审核可以帮助作者修改代码，但只有 PR 中绑定当前 head 的审核结果才能参与合并决策。

## 3. 审核输入

AI 审核上下文必须明确记录：

- PR 编号、`base_sha`、`head_sha`、changed files 和事件类型；
- 当前变更直接引用的 Spec、接口契约、配置和 progress 声明；
- 受影响测试、CI workflow、历史失败证据和相关 artifact；
- 作者提供的目标、非目标、兼容性说明和测试命令；
- 审核使用的模型、版本、提示模板、工具和时间。

上下文按 changed files 最小化选择。不得把无关历史文档、未验证的聊天内容或其他 PR 的结论当作当前变更要求。Secret、API key、个人数据和未授权的生产数据不得进入审核上下文。

## 4. 审核维度

AI 必须逐项判断“适用/不适用”和证据来源：

1. **目标与 Spec**：实现是否满足变更目标，是否违反当前 Spec、接口契约或阶段边界；
2. **正确性**：正常路径、边界输入、失败关闭、重试、幂等和并发行为是否正确；
3. **兼容性**：公共 API、Schema、配置、旧入口、数据格式和跨平台行为是否回归；
4. **测试与证据**：测试是否覆盖实际风险，命令是否针对当前 diff，结果是否对应当前 `head_sha`；
5. **安全边界**：Secret、权限、Workflow、外部命令、不可信输入、容器和网络访问是否扩大风险；
6. **运行与可观测性**：超时、取消、日志、错误信息、回滚和故障定位是否足够；
7. **维护性**：重复逻辑、死代码、隐式全局状态和与仓库既有约定明显冲突的实现。

对于网页、CLI、服务或其他可运行产品，AI 可以在隔离环境中执行最小复现、查看输出、截图或调用只读工具；运行结果必须作为证据保存，不能用截图代替单元测试、契约测试或安全检查。

## 5. 问题等级

AI 使用以下问题等级，不与 CI 的 `pass/fail/blocked` 混用：

| 等级 | 定义 | 默认处理 |
|---|---|---|
| `blocker` | 必然导致错误行为、数据损坏、权限绕过、Secret 暴露、错误合并或无法安全发布 | 必须修复，不能普通审批豁免 |
| `high` | 高概率造成用户可见回归、公共契约破坏、严重性能/可靠性问题或安全边界不清 | 必须修复，或由模块 owner 与安全审核者书面接受 |
| `medium` | 有明确触发条件的功能缺口、测试不足或维护风险 | 修复，或由模块 owner 记录限期例外 |
| `low` | 可改进的风格、可读性或非阻断维护建议 | 可选，不得伪装成阻断问题 |

每条问题还必须有 `confidence=high|medium|low`。低置信度问题默认是 `review_required`，不能直接阻断合并；但涉及安全、权限或数据完整性的低置信度信号必须升级给人工安全审核者。

## 6. 有效问题格式

每条 finding 至少包含：

```json
{
  "id": "AI-001",
  "severity": "high",
  "confidence": "high",
  "category": "correctness|compatibility|test|security|operations|maintenance",
  "file": "src/example.py",
  "line": 42,
  "trigger": "具体输入、事件或环境",
  "expected": "应有行为",
  "actual": "当前行为",
  "evidence": ["命令、日志、测试或代码路径"],
  "recommendation": "可执行的修复建议",
  "status": "open|fixed|accepted|false_positive|review_required"
}
```

缺少定位、触发条件或证据的问题只能作为审查问题记录，不能作为确定性阻断结论。AI 不得用“看起来”“可能有问题”直接替代可复核说明。

## 7. 标准审核流程

1. **准备上下文**：固定 base/head SHA，收集最小相关 Spec、代码、测试和 CI 证据。
2. **独立首轮审核**：AI 先只看目标、约束和 diff，再按审核维度检查，不继承作者或前一轮 AI 的结论。
3. **最小验证**：对高置信度问题运行相关测试、静态检查或隔离复现；不能验证时标为 `review_required`。
4. **输出报告**：生成结构化 `ai-review.json` 和可读报告，按严重程度排序，明确没有检查的范围。
5. **作者处理**：作者逐条标记修复、接受、误报或需要人工判断，并提供对应 commit、测试或理由。
6. **复核变更**：AI 只复核新 diff、原问题位置和受影响测试；修复后必须确认没有引入新的高风险回归。
7. **结束审核**：最多进行 4 轮自动复核；同一问题在已有证据不变时不得重复提出。超过轮次仍有争议时转人工审查。
8. **风险聚合**：将未关闭 finding 和 CI/安全结果交给 [变更风险策略](risk-policy.md)，再按 [人工审批策略](approval-policy.md) 路由 reviewer。

## 8. 通过条件

AI 审核只能形成以下三种结论：

- `pass`：没有未处理的 `blocker`/`high`，且没有需要人工裁决的安全或权限问题；
- `review_required`：存在低置信度、范围不清或作者与 AI 结论不一致的问题，必须进入人工审核；
- `fail`：存在已确认的 `blocker`，或存在未处理的高危安全问题。

`pass` 只表示 AI 审核没有发现达到阻断条件的问题，不表示代码正确、测试完整或可以直接合并。最终合并仍要求 CI 通过和人工审批满足。

## 9. 工具和权限边界

- 默认只读 checkout；运行测试使用隔离环境和最小权限；
- 可以读取当前 PR 的代码、Spec、测试、CI 日志和 artifact；
- 不得读取 Secret、修改 Branch Protection、批准/合并 PR、推送分支或修改生产系统；
- 浏览器、截图、服务调用等运行验证必须指向隔离环境，并记录命令、输入和输出；
- 外部模型或工具失败、超时、上下文不完整时输出 `blocked` 或 `review_required`，不能假定通过。

## 10. 与其他审核的关系

- CI 负责确定性门禁和当前 head 的 `pass/fail/blocked`，详见 [CI 执行子系统 Spec](../ci/spec.md)；
- AI 审核负责代码风险发现、复现和审查证据；
- 安全审核负责 Secret、依赖、权限和不可信代码边界；
- 人工审核负责接受风险、裁决争议和最终批准；
- Harness/Evaluation 负责评测、评分、Replay 和长期 evidence，不被 AI 审核报告复制。
